# 已知局限与真实基准对比数据

本文件记录 `repomap_lite` 相对真实 tree-sitter 版 `repomap`（`ariadoss/repomap`）
的实测差距。所有数据来自真实开源项目的实际运行结果，不是理论推测——每一条
记录都能追溯到具体的源码行、触发条件、修复方式和重新验证的结果。

方法论：clone 真实的 `ariadoss/repomap`，在装好 `tree-sitter`/`tree-sitter-languages`
依赖的环境里生成基准输出；`repomap_lite` 则在**确认不含 tree-sitter 的干净
venv** 里运行，避免两边环境互相污染。用符号名集合做 precision/recall 对比，
而不是逐行文本 diff，因为两者的格式细节本来就不同（真实基准会展示函数体的
2-4 行预览，`repomap_lite` 目前不会）。

**两种对比口径，都如实报告，不只挑好看的数字**：
- **raw（全部内容行）**：把两边输出里每一个 `│` 前缀行（不管缩进层级）都拿来抠
  符号名对比。这是最保守、最不会漏掉真实差异的口径，但会把真实基准展示的
  "函数体预览行"（比如 `var length = str.length;` 这种局部变量，只是因为
  出现在预览窗口内被顺带展示）也当作"独立符号"计入对比，导致 precision/recall
  都比实际情况偏低。
- **flat-only（仅顶层/列0内容）**：只比较不带缩进的行。能剔除大部分"函数体预览
  噪音"，数字通常更接近真实的符号识别能力，但对某些语言结构不适用——比如
  C# 代码几乎全部包裹在 `namespace X { ... }` 里，真正的类/方法定义本身也是
  "缩进"的，flat-only 口径会把几乎全部真实内容都当作噪音过滤掉，产出没有
  参考价值的数字（甚至可能是 0/0）。**遇到这种情况一律改用 raw 口径**，
  本文件对每种语言都注明了实际使用的口径。

**C 语言 `.c`/`.h` 数字的一次修正说明**：上表当前的 C 语言数字来自一次
独立第三方复核，用他们自己写的对比脚本重新measure、并且公开了脚本本身
（脚本比本项目此前用的诊断脚本更完整——尤其是对 C 风格"返回类型 函数名(...)"

precision 数字从 86.9% 改成了 37.8%，方向是往下修，不是往上**——核实后
发现本项目此前用来生成"86.9%"这个数字的诊断脚本，在解析 tree-sitter
基准的原始输出时对复杂头文件（含大量函数原型声明）的符号名抽取本身不够
完整，导致分子分母同时被低估，凑巧算出一个偏乐观的比值。换成第三方更完整
的抽取逻辑后，`.h` 文件的真实差距（大量真实函数原型被参考基准遗漏，见下文
专门章节）才完全暴露出来。这个教训跟本文件前面记录的其它几次"用于验证的
脚本本身有 bug"是同一类问题，再次印证：**衡量精度的工具本身也需要被
独立验证，不能默认自己写的诊断脚本是准的**。

**跟本文件上一版相比的变化幅度**（本轮会话修复前 → 修复后，用相同 raw 口径对比）：
- C：`.c` 扩展名此前完全未注册，精度事实上是 0%；修复并叠加后续多个 bug
  修复后，`.c` 文件（合并统计里权重最大的部分）稳定在 98%+ precision；
  `.h` 文件的数字持续偏低，但已确认主要是参考基准自身对函数原型声明识别
  不全导致（见上文"C 语言 `.c`/`.h` 数字的一次修正说明"和下文专门章节），
  不是 `repomap_lite` 的真实回归
- C++：43%（此前 ~36%，本轮进一步修复了字符串/注释交互问题）
- Qt/C++：78.5%（此前 70.1%）
- Java：98.9%/86.5%（此前 98.4%/76.4%，`throws` 子句修复生效）
- JS：precision 从 ~51% 提升到 ~97%（函数体作用域追踪 bug 修复，是本轮最大的单项提升）
- Rust：全新支持，从完全不支持到 flat-only 口径 100%/99.2%
- Ruby：全新支持，无历史数字可比较

C++（nlohmann/json）依然是表现最弱的一档，原因不是某个具体 bug，而是该项目
大量使用宏和模板元编程，是正则方案面对这类代码的系统性局限（详见下文）。

## Ruby：参考基准本身存在方法提取缺口（重要，影响如何解读 Ruby 的数字）

本轮会话新增 Ruby 支持后，第一次跑真实项目（Jekyll，159个文件）对比时，
精度数字异常低（39.3%），远低于其他所有已支持语言。按照本项目一贯的原则
——"数字反常时先怀疑测量方法，再怀疑被测系统"——没有直接把这个数字当作
"Ruby 适配器质量差"的结论，而是逐层排查，发现根因完全在参考基准
（`ariadoss/repomap`）这一侧：

**参考基准的 tree-sitter Ruby 语法支持本身有系统性缺口**：统计发现 159 个
文件里，有 110 个文件参考基准展示的内容里**一个 `def` 方法都没有**——
只展示 `module`/`class` 声明本身。抽样检查了其中 20 个"零方法"文件，
**17 个在真实源码里确实包含正常的 `def` 方法定义**，说明这不是"这些文件
本来就没有方法"，而是参考基准的解析器在处理它们时就是没能把方法提取出来。

进一步定位到至少两个具体触发条件（不是详尽列表，只是找到的已确认案例）：
1. **`%r!...!` 风格的正则字面量**（Ruby 允许用任意分隔符写正则，`%r!pattern!`
   是常见写法之一）：真实文件 `lib/jekyll/document.rb` 里有一行
   `%r!\A(---\s*\n.*?\n?)^((---|\.\.\.)\s*$\n?)!m.freeze`，这行之后，
   参考基准展示的该文件内容就只剩 `module`/`class` 声明，后续全部方法
   消失。
2. **`class << self` 单例类语法**（Ruby 定义类方法的一种写法）：真实文件
   `lib/jekyll/drops/drop.rb` 里的 `class << self ... end` 块，同样导致
   该文件里几乎全部方法（包括这个块内部和块外部的）都没有被参考基准展示。

而且这个缺口比"按文件出问题"更细粒度——`lib/jekyll/tags/include.rb` 一个
文件里有多个 class，其中一个 class（其内部含 `%r!` 正则）后续方法全部
丢失，但文件里另一个 class 的方法却被正常提取，说明参考基准的解析器
错误恢复能力有限，一旦在某处"绊倒"，从那里往后的内容都可能受影响，
不管是不是同一个 class。

**这如何影响你该怎么用 Ruby 的数字**：
- **Recall（91.5%，全部文件）是可信的、有意义的数字**——它衡量"参考基准
  展示的内容里，本工具找到了多少"，不受基准缺口影响（基准漏掉的内容，
  recall 计算时也不会去找，所以这个方向的比较是公平的）。
- **Precision（39.3%，全部文件）不能直接采信**——它衡量的很大程度上是
  "本工具找到了多少参考基准由于自身缺口而没有展示的真实内容"，也就是说
  这个数字低，恰恰反映的是本工具比参考基准更完整，而不是本工具有更多
  误报。限定到参考基准自己能正常提取方法的 49 个文件后，precision
  回升到 71.1%，这个数字更接近"本工具真实精度"的合理估计，但由于筛选出
  的这 49 个文件本身可能是"参考基准处理得比较顺利的简单文件"这一有偏
  样本，71.1% 也未必是全貌，只是比 39.3% 更值得信任。

这条记录本身也是一条方法论经验：**任何用来验证的参考基准工具都可能有
自己的局限，尤其是覆盖冷门语言/语法变体时**；本轮会话里 C 语言相关的
几次数字反常最终也确认是对比脚本自身的问题，Ruby 这次则是参考基准
本身的问题，两者都提醒不要把第三方工具的输出直接当作绝对真值。

## C 头文件：参考基准同样存在函数原型提取缺口（跟 Ruby 那条同类型的发现）

独立评审用 Redis 语料（含 hiredis/jemalloc/lua/tre 等真实 C 依赖库，744个
文件）重新测量时发现：早期报告的"整体精度82.3%"把 `.c` 和 `.h` 文件混在
一起统计，掩盖了两种完全不同性质的情况。拆开后（数字已按后续独立复核
修正，见前面"C 语言 `.c`/`.h` 数字的一次修正说明"）：

| 文件类型 | Precision | Recall |
|---|---|---|
| `.c` 文件 | 98.5% | 85.7% |
| `.h` 文件 | 37.8% | 91.6% |

**`.h` 文件精度数字低的真相**：逐条核实后发现，被标记为"多余/误报"的
`.h` 符号里，很大比例其实是**头文件里的函数原型声明**（如
`void redisAsyncFree(redisAsyncContext *ac);`），这些是真实存在、语法
完全正确的符号——问题出在**作为对比基准的 tree-sitter 参考实现
（`ariadoss/repomap`）本身对"只有声明没有函数体"的原型识别不完整**，
导致基准本身漏掉了这些符号，让 `repomap_lite` 正确识别的内容被误判为
"多余的误报"。这条结论用两个独立文件验证过，不是单一样本的巧合：

- `deps/hiredis/async.h`：约20个真实函数原型（`redisAsyncConnect`、
  `redisAsyncFree`、`redisAsyncCommand` 等），参考基准只识别出1个
  （`redisAsyncSetTimeout`），`repomap_lite` 正确识别出全部约19个。
- `src/quicklist.h`：源码里约30-40个真实函数原型（`quicklistCreate`、
  `quicklistAllocSize`、`quicklistBookmarkCreate` 等），参考基准
  **一个都没有识别**（该文件在基准输出里只展示了几个 `typedef struct`
  的字段预览，零函数），`repomap_lite` 正确识别出26个以上。

这两个案例里 `repomap_lite` 都是**更完整的一方**，不是更差的一方。这跟
本文件前面"Ruby：参考基准本身存在方法提取缺口"那条发现是同一类问题
（参考基准对某些语法形态的覆盖有系统性缺口），只是这次出现在 C 头文件的
纯声明（无函数体）这个场景。

**这如何影响你该怎么用 `.h` 文件的精度数字**：跟 Ruby 那条的结论类似，
`.h` 文件的 precision 数字（37.8%）里，被算作"误报"的绝大部分实际上是
本工具比参考基准更完整的正确识别，不能直接当作"本工具有更多误报"来解读。
如果排除参考基准自身遗漏原型声明造成的虚假"误报"，真实 precision 应该
高得多，但由于没有独立的、验证过原型声明识别能力的第三方基准可用，
无法给出一个更精确的数字，如实记录这个局限——这也是为什么本文件不建议
在"提高 `.h` 文件精度数字"这个方向继续投入 `repomap_lite` 自身的开发
精力，真正的瓶颈在评测方法论，不在被测代码。

## 本轮会话修复的问题（按语言分组，每条都有真实项目复现证据）

### C 系语言（C#/Java/C++/Qt）共用的适配器

**1. `.c` 扩展名完全未注册**：C-family 适配器的 `cpp` 方言扩展名列表里没有
`.c`，纯 C 项目（如 Redis 的核心代码，474 个 `.c` 文件）100% 被跳过。修复：
补上 `.c` 扩展名。这不是精度问题，是覆盖范围问题——影响面直接从"部分功能
打折"变成"整个语言类别完全不可用"，是本轮修复优先级最高的一项。

**2. 单行方法体完全无法匹配**（`void Foo() { }`）：方法识别正则的收尾部分
只允许一个可选的 `{`/`;` 后接空白到行尾，从未考虑花括号在同一行内配平的
写法，末尾多出的 `}` 破坏了正则的结尾锚点。这个 bug 影响面很大，因为单行
方法/getter/setter 在真实代码里极其常见。用 C# 嵌套类测试案例复现确认。

**3. 帧栈"卡死"问题**（连续出现三次，每次触发条件不同）：
- 同一行内 `{ }` 配平的方法体会导致"函数体屏蔽帧"的深度从未真正超过
  基线，永远无法被判定为"已进入"从而永远无法弹出，后续整个文件都被误判为
  "仍在函数体内部"。修复：新增 `line_is_brace_balanced()` 检测。
- **C 语言的前向声明**（`struct redisObject;`，只有声明没有花括号体）被
  误判为"开启了一个等待花括号体的容器"，同样导致帧永久卡死。用真实项目
  Redis 复现：`src/server.h` 一个文件里因为开头几个前向声明，导致后面
  几乎全部内容（本该识别出 1200+ 符号）只识别出 8 个。这是本轮修复里
  单项收益最大的一个 bug。

**4. `Class::Method(...)` 类外实现写法**、**构造/析构函数无返回类型**、
**Java 的 `throws` 子句**：三个独立的正则覆盖缺口，分别用 C++/C#/Java 真实
项目复现确认，修复方式是各自新增专门的正则规则或收尾片段。

**5. 返回类型独占一行的写法**（`static void\nfoo() {`，Linux kernel/jemalloc
等大量代码库的主流风格）：早期完全不支持，且首次修复时用的"类型独占一行"
判断只认识固定的几个关键字（`static`/`inline`/`extern`/`const`），无法识别
项目自定义的宏前缀（如 jemalloc 的 `JEMALLOC_ALWAYS_INLINE void`）。改成
接受任意标识符序列后修复，但要额外排除 `return` 等控制流关键字单独占一行
的情况，避免误判。

**6. `typedef` 完全不支持**：包括简单别名、函数指针别名
（`typedef void (*name)(args);`）、匿名 struct/enum 跨行 typedef
（`typedef struct { ... } Name;`，名字在收尾行才出现，需要跨行状态追踪）。
用 Redis 内嵌的 jemalloc/xxhash 头文件复现确认三种形式都很常见。

**7. 注释与字符串屏蔽的相互干扰**（本轮反复出现的同一类根本问题，共 3 个
独立触发场景）：
   - C# 逐字字符串 `@"...{...}..."` 里写死花括号字符，被朴素花括号计数误判
     为真实嵌套（Newtonsoft.Json.Tests 复现，一个文件因此 recall 从 82.9%
     升到 99.6%）。
   - **英文注释里的撇号**（`/* the caller's buffer */`）被误判为字符字面量
     开始，如果撇号和后续某个真实字符字面量凑巧"配对"，会连带吞掉注释自己
     的收尾符 `*/`，导致文件从这里往后全部被误判为仍在注释内（Redis
     `src/cluster.c` 复现）。
   - **字符串内容里恰好出现 `*/*` 这样的三字符序列**（`.set('Accept', '*/*')`,
     express 测试代码复现），被朴素扫描器误判为"这里有 `/*` 开启了块注释"
     （从中间的 `/` 往后读恰好构成 `/*`）。
   
   这三个场景共同确认了一个架构结论：**注释和字符串的语法边界互相依赖对方
   的状态才能正确判断，任何"先处理字符串再处理注释"或反过来的两阶段流水线
   都会在某个阶段对另一个阶段负责的语法产生误判**。最终修复统一为一次线性
   扫描、一套状态机同时处理两者（`mask_c_family_comments_and_strings`）。

### JavaScript/TypeScript

**8. 顶层声明规则的作用域判断完全错误**（本轮修复中收益第二大的 bug，
把 lodash/express 的 precision 从 ~51% 拉到 ~97%）：早期版本判断"是否顶层"
只看"有没有进入 class/interface"，完全没有考虑"是否身处任意一个普通函数体
内部"。真实后果两个：
   - lodash.js 整个文件被 `;(function() { ... })();` IIFE 包裹，内部的
     `var VERSION = '4.18.1'` 这类内部实现常量被误判为顶层声明收录
     （单文件 297 个，是精度崩溃的直接原因）。
   - express 测试代码里 `var app = express();` 出现在多层嵌套的
     `describe(...)`/`it(...)` 测试回调内部，同样被误判为顶层声明。
   
   修复：新增独立的"函数体深度栈"，区分"是否在任意函数体内部"（包括匿名
   回调、IIFE，不只是具名函数），只有确认不在任何函数体内时才允许顶层
   声明规则生效。

**9. 同样的注释/字符串屏蔽相互干扰问题**：JS/TS 适配器早期用独立的
`strip_block_comments()`，不感知字符串边界，撞上了跟 C 系语言完全同源的
问题（`'*/*'` 字符串被误判为注释开始）。修复：改用同一个统一的
`mask_c_family_comments_and_strings`（已扩展支持模板字符串）。

**10. Interface 字段列表不做数量限制**：早期版本会把 interface 的每一个
字段都展示为独立符号，字段数量没有上限。真实基准的行为是最多展示 3 行
预览就截断（用 `⋮` 表示还有更多）。这不只是"跟基准对齐"的问题，也直接
影响输出体积——大型 interface（几十个字段）会让符号数随字段数线性增长。
修复：class/interface 的字段收集加上 3 条的展示上限，class 方法（更重要的
信息）不受此限制。

**11. 顶层解构声明不识别**：`const { Buffer } = require(...)` 这类解构赋值，
早期正则只接受纯标识符，不接受花括号/方括号模式。

### Rust（本轮全新支持的语言）

**12. Rust 生命周期标注被误判为未闭合字符字面量**：`'static`、`'a` 这类
生命周期标注用单引号开头但不闭合，最初复用 C 系的字符串屏蔽逻辑，把
生命周期标注误判为未闭合字符字面量，吞掉所在行剩余内容——包括函数返回
类型后面的 `{`。用 ripgrep 的 jemalloc 风格代码复现：一个文件因此从
1200+ 符号骤降到 8 个。

**13. 原始字符串 `r"..."`/`r#"..."#` 与嵌套块注释**：Rust 的原始字符串
（内容不转义、可跨行、井号数量可变）和嵌套块注释（`/* /* */ */`，C 系
语言不允许嵌套但 Rust 允许）都是 C 系语言没有的语法元素。最初尝试用独立
预处理阶段处理这两点，各自单独测试都通过，但组合在一起时出现了第三个
问题：**判断"这是不是一个原始字符串"依赖"当前是否已经在注释里"这个
上下文**，独立预处理阶段天然不知道自己是否身处注释中——真实案例：
`/*! ... "search worker" ... */` 文档注释里，"worker" 结尾的字母 `r` 加
紧跟的引号 `"` 恰好拼出看起来像原始字符串开头的 `r"`，被独立的原始字符串
扫描器误判，导致该文件全部内容被误吞。这是"注释与字符串边界互相依赖"这个
教训在 Rust 上的第三次重演，最终统一为单个 `mask_rust_source()` 函数，
在一次线性扫描里同时处理全部语法元素（行注释/嵌套块注释/普通字符串/
原始字符串/字符字面量/生命周期标注）。

**14. `const fn` 不识别**：`const fn foo() { ... }` 是 Rust 的编译期可求值
函数，函数识别正则最初只接受 `pub`/`async`/`unsafe`/`extern "..."` 前缀，
不认识 `const` 修饰符。用 ripgrep 复现确认。

### Ruby（本轮全新支持的语言）

Ruby 的嵌套结构靠关键字配对（`def`/`class`/`module`/`if`/`while`/`do`
等开启块，`end` 收尾），是本项目支持的第三种嵌套范式（花括号/缩进/
关键字配对）。开发适配器本身没有像 C 系/Rust 那样经历"改了三次才对"的
反复，主要因为提前应用了本项目已经验证过的经验（字符串/注释屏蔽必须
在同一次线性扫描里统一处理，一次写对），但真实项目验证过程本身发现了
一个上一节已经详细记录的重要问题（参考基准的 Ruby 支持有方法提取缺口），
不重复列在这里。

已用真实测试确认正确处理的 Ruby 特有陷阱（没有触发 bug，记录下来是因为
这些是 Ruby 相比其他语言明显更容易出错的地方，值得在文档里明确"已验证
没问题"，而不是留白让人怀疑）：
- 单行 `if`/`unless` 修饰符（`return unless valid?`）正确识别为不开启块，
  跟块形式的 `if...end` 区分开
- `do...end` 代码块（`[1,2].each do |x| ... end`）正确追踪深度但不生成
  虚假符号
- 字符串插值 `"#{expr}"`（含插值内部嵌套花括号/方法调用）正确处理
- `=begin`/`=end` 块注释正确识别，且验证过注释内容里故意写的"end"、
  "class Foo"等陷阱文本不会误触发
- 单行定义 `class Foo; end` 正确识别，且验证过后续代码不会被误判深度

### Makefile（本轮全新支持的格式，非传统编程语言）

**15. 目标专属变量赋值被误判为独立 target**：GNU Make 允许
`target: VAR ?= value` 这种"目标专属变量赋值"语法，跟真正的
`target: 依赖列表` 长得一样（都是"标识符 冒号 内容"的形式），但语义
完全不同——前者只是给这个目标构建时设置一个局部变量。用真实项目 Redis
的顶层 Makefile 复现：`install: SKIP_BUILD ?= 1` 和紧随其后的
`install: deploy`（真正的依赖声明）如果都展示为独立 target，会让读者
误以为存在两个不同的 `install` 定义。修复：检测冒号后的内容是否是
"标识符 + 赋值操作符(`?=`/`:=`/`+=`/`=`)"这种形式，是则跳过。

**这个修复过程中差点引入了一个更糟的问题，记录下来提醒以后不要重蹈覆辙**：
最初尝试的修复方案是"同一个 target 名字只展示一次，后续重复的都跳过"，
这个方案能解决上面的具体案例，但会错误吞掉合法的 GNU Make 写法——同一个
target 分成多行声明依赖是完全合法且常见的（`build: main.o` 和
`build: utils.o` 分两行写，依赖会累加，不是互相覆盖）。用这个具体场景
手动验证后发现"按名字去重"确实会丢失第二行的真实依赖信息，所以放弃了
这个方案，改成更精确的"只过滤看起来像变量赋值的那一种形式"，不做任何
基于名字的去重。这个教训本身值得强调：**修复一个误报时，要先构造一个
"看起来会被新逻辑误伤的合法场景"去验证，而不是想当然地认为修复没有副作用**。

### Dockerfile（本轮全新支持的格式，非传统编程语言）

无历史 bug 记录——第一次实现就用真实项目场景（多阶段构建、无 AS 子句的
单阶段构建、`ARG` 变量插值、引用早期阶段作为后续阶段基础镜像）验证通过，
没有发现需要修复的问题。

### C 系语言的两个后续修复（独立评审针对性复测后发现，跟前面7条属于同一个
适配器但是后续独立的一轮）

上面 C 系语言的第1-7条是本轮会话前半程的修复；这两条是后续针对"C系精度
不够"这个反馈做定向复测（用 Redis 语料含 hiredis/jemalloc/lua/tre 等
真实依赖库）时新发现、新修复的，记录在这里而不是混进前面的编号列表，
避免打乱已有的编号引用。

**16. 多行参数列表跨越三行以上时，帧栈状态判断错误导致文件级别的连锁
错位**：早期的"返回类型独占一行"修复（上面第5条）只处理了2行的情况
（返回类型一行、函数名+完整参数一行）。真实项目 jemalloc 里大量出现
3行形式：返回类型一行，参数列表本身又跨2行，例如：

```c
static void
arena_maybe_do_deferred_work(tsdn_t *tsdn, arena_t *arena, decay_t *decay,
    size_t npages_new);
```

早期判断逻辑只检查"当前处理的这一行是否以 `;` 结尾"来决定要不要压入
一个"等待函数体"的帧——第2行（参数列表中间）显然不以 `;` 结尾，被
误判为"即将有函数体"，压入一个永远等不到左花括号的帧，这个帧从此
卡死在栈顶，导致文件从这里往后的全部内容都被误判为"仍在某个函数体
内部"而被跳过。用真实文件 `deps/jemalloc/src/arena.c` 复现确认：
修复前该文件大量后续函数完全无法识别，表现为渲染输出里出现大量看起来
是"裸露的 `void`/`int` 独立一行"的异常内容（这些实际上不是独立的假
符号，而是被压缩到一行显示的多行签名的第一行，本身没有生成假符号，
但真正的问题——后续内容因帧栈卡死而丢失——是真实的）。修复：新增
`_find_statement_terminator()`，遇到函数签名匹配上时，不再只看当前行
是否以 `;` 结尾，而是从签名开始处的第一个 `(` 做括号计数，找到真正
配对的 `)`，再看紧跟其后的第一个非空白字符是 `;`（纯声明，不压帧）
还是 `{`（有函数体，压帧），从根本上不依赖"当前行长什么样"这个不可靠
的信号。

**17. 返回类型和函数名同一行、但参数列表跨行时完全无法识别，且会连带
产生真实的误报符号**：这是跟上一条相关但独立的另一种写法——不是"返回
类型独占一行"，而是"返回类型+函数名在同一行，参数列表从这一行开始
但跨到下一行才结束"，例如：

```c
static redisContext *getRedisContext(const char *ip, int port,
                                     const char *hostsocket)
{
```

早期的方法识别正则要求参数列表 `(...)` 在同一行内配平（正则用
`[^;{}]*` 限定括号内容，天然无法跨行匹配），所以这种写法完全匹配不上
任何规则——`getRedisContext` 本身既不会被识别为符号，也不会被当作
"进入了一个函数体"，导致后续深度追踪从这一行开始就是错的。用真实项目
Redis 复现的具体后果（`src/redis-benchmark.c`）：`getRedisContext`
函数体内部的语句（`else` 分支、`fprintf(stderr, ...)` 调用）因为深度
判断错乱，被误判为顶层内容重新触发符号识别，产出真实的假符号
（内容形如 `else` 单独一行、`fprintf(...)` 调用语句），这是独立评审
报告里具体点名的误判案例，且实测统计过这类调用语句误判在全量语料
上一度有一定数量。修复：新增 `_UNCLOSED_PAREN_SIGNATURE_RE`，当通用
方法正则和"返回类型独占一行"规则都匹配不上、且当前行确实有未闭合的
左括号时，尝试把这一行当作"函数名+参数列表跨行"的信号，同样用
`_find_statement_terminator()` 跨行查找真正的收尾字符来确认。

**这两条修复后的实测效果**：全量 Redis 语料（744个可映射文件）里，
`fprintf`/`memcpy` 等函数体内部语句被误判为顶层符号的情况，从独立评审
报告的"仅 fprintf/memcpy 两项就350处"降到 0（第三方独立复核用他们自己
的对比脚本重新验证过，`.c` 文件误报数字进一步降到156处，且全部逐条
核实为其他更细小的成因，不再包含 K&R 签名或 libc 调用泄漏这两类）；
`.h` 文件的精度数字仍然明显偏低（37.8%），但已确认这主要是参考基准
自身对函数原型声明识别不全导致，不是这两条修复本身遗留的问题（见前面
"C 头文件：参考基准同样存在函数原型提取缺口"一节）。

**独立复核确认**：这两条修复后来经过一次独立的第三方复核（用他们自己
重写、更完整的对比脚本，公开了脚本本身），确认：
1. K&R式返回类型独占一行的最小复现案例（`static inline void\nswapfunc(...)`）
   正确合并为一个符号，不再产出裸符号 `void`；本项目用同样的案例加上
   全量 Redis 语料（786个 `.c`/`.h` 文件）扫描复现确认零残留。
2. `fprintf`/`memcpy` 类函数体内语句泄漏，在全量语料扫描下确认为 0 处
   （不只是复核方测到的样本子集）。
3. 复核方特别指出实现方式比他们最初建议的"libc函数名黑名单"更根本——
   用的是通用的语句边界判断（`_find_statement_terminator`/
   `_paren_balance`），不针对特定函数名，覆盖面更广。这个评价符合实际
   设计意图：黑名单方案治标不治本，只能挡住已知的高频误判源，根因修复
   能覆盖任何形状类似的语句，不局限于 `fprintf`/`memcpy` 这两个具体名字。

**副产品**：C 系适配器在这轮修复过程中，还补上了 `typedef struct {...}
Name;`（匿名）和 `typedef struct Tag {...}`（具名）这类跨行 typedef 块
的正确闭合匹配，是用真实项目 Redis 内嵌的 `xxhash.h` 验证过的场景——
这是排查上述两个机制时顺带发现、之前未被任何一轮 review 明确点出的
真实缺口，不是本次修复计划内的目标，记录在这里说明修复过程本身也在
主动扩大测试覆盖，而不只是被动响应已提出的问题清单。

**这两条修复带来的一个方法论确认**：独立评审报告最初把"K&R式返回类型
独占一行"和"函数体内裸调用语句误判"描述成两个并列独立的问题，本轮
复现后发现后者在很大程度上是前者（更准确说是前者的一个未覆盖变体，
即第17条）造成的连锁后果，不是完全独立的第二套机制——修复了根因
（帧栈状态判断）之后，下游症状（`fprintf`/`memcpy` 假符号）绝大部分
自然消失，只是恰好还有一种前者没覆盖到的具体多行签名写法（第17条）
需要单独补一条规则。这提醒复测时不要想当然地假设"报告里列的每一条
现象都对应一个需要独立修复的机制"，现象之间可能有因果关系，先修根因
再看下游症状是否还残留，往往比逐条现象各写一个补丁更高效。

## 完全不同于编程语言符号的两种格式：Makefile / Dockerfile

这两种格式**没有真实基准可以对比**——`ariadoss/repomap`（本项目用作
真值来源的参考实现）完全不支持这两种格式，所以本节不像上面各语言那样
报告 precision/recall 数字，而是如实说明"提取的是什么、为什么这么选、
覆盖到什么程度"，具体见 SKILL.md 的"输出格式"一节和两个适配器
（`makefile_adapter.py`/`dockerfile_adapter.py`）文件内的详细文档字符串。

简要提炼：
- **Makefile**：提取 target（可执行目标），不提取变量赋值——因为
  "这个项目有哪些可以跑的操作"比"内部用了哪些配置变量"对冷启动理解
  更有信息量。已知局限：模式规则（`%.o: %.c`）按普通 target 展示，
  不做模式规则语义标注；多行 target（反斜杠续行的依赖列表）只识别
  声明行本身。
- **Dockerfile**：只提取 `FROM ... AS stage`（多阶段构建的阶段划分），
  不提取 `RUN`/`COPY`/`CMD` 等具体步骤指令——同样是"项目怎么构建/部署"
  这个更高层次的信息比逐条构建指令更有冷启动价值。已知局限：不解析
  `ARG` 变量插值的实际取值，原样展示插值表达式文本。

## `.gitignore` 支持（用户反馈后新增，非某次系统性复测发现）

早期版本只有一份写死的目录名黑名单（`node_modules`/`vendor`/`dist`等），
完全不读项目自己的 `.gitignore`。这在两个方向上都不对：项目自定义命名
的生成目录（比如 `custom_generated/`，或者不叫 `dist` 本身的路径）不会
被排除，会被完整扫描并出现在 REPOMAP.md 里；反过来硬编码名单也无法
感知项目明确想要保留的同名目录。用户直接指出"生成的时候有没有考虑
.gitignore，npm modules这种压根不需要看"后，用一个最小复现案例
（`.gitignore` 里写 `custom_generated/`，该目录下的 `.py` 文件此前会被
完整扫描并出现在输出里）验证确认是真实缺口，随即实现并验证。

**实现范围**（`.gitignore` 规则里最常用、价值最高的子集，不是 git 官方
完整规范）：
- 逐行读取 pattern，跳过空行和 `#` 注释
- 行尾 `/` 表示"仅匹配目录"
- 前导 `/` 表示"仅相对仓库根目录匹配"
- `*`/`?` 通配符
- `!` 开头的否定模式（取消之前规则的排除）
- 嵌套 `.gitignore`（每个目录自己的 `.gitignore` 只影响该目录及其子树，
  这是 git 的真实行为，也是很多 monorepo 实际依赖的行为）

用四个独立场景验证过：自定义命名目录排除、通配符模式（`*.local.py`）、
否定模式（`logs/*` 加 `!logs/important.py`，验证只有 `important.py`
存活）、嵌套 `.gitignore`（子目录的规则不影响父目录内容）。另外在真实
Redis 语料（含15个嵌套 `.gitignore`）上验证过不会误删任何真实源码文件
——该语料的 `.gitignore` 主要针对编译产物（`.o`/`.so`/二进制文件），
跟已支持语言的源码扩展名没有交集，扫描结果与开启前完全一致（逐文件
diff 确认零差异），说明这个功能在真实项目上是安全的，不会意外压低
recall。

**已知局限**（这些是 git 官方 `.gitignore` 规范里相对少见的写法，跟
已知局限一贯的原则一样——覆盖不到时选择"不误删"的方向，把局限记录
清楚，而不是为了追求完整语义引入更高的实现/维护成本）：
- 不完整实现 `**` 的多层目录匹配语义（按普通通配符处理，在深层嵌套的
  边界情况下可能跟真实 git 判断不完全一致）
- 不处理全局 gitignore 配置（`core.excludesFile`）或 `.git/info/exclude`
- 否定模式的优先级简化为"按声明顺序，后面的规则覆盖前面的"，没有完整
  实现 git 规范里"父目录已被排除时否定模式失效"这条边界规则
- `--include-vendor` 和 `--no-gitignore` 是两套独立的开关，分别控制
  硬编码目录黑名单和 `.gitignore` 读取，不要混淆——关掉一个不会影响
  另一个继续生效

## `.gitignore` 支持的一个真实正确性 bug（用真实项目"构建+调试运行后"场景测出）

上面记录的验证（自定义目录/通配符/否定模式/嵌套 `.gitignore`/Redis
语料）都是在**干净的仓库状态**下做的，没有真正验证过"构建产物已经生成、
调试服务已经跑起来"这种更贴近真实使用场景的脏状态。用户建议直接拿一个
真实项目（`randomgitsrc/peekview`，Python 后端 + Vue 前端）实测这个场景，
过程如下：

1. clone 仓库（3407个源文件）
2. 真实执行前端构建（`npm install` + `vite build`，产出压缩后的 JS/CSS
   资源，含 Shiki 语法高亮的语言包、Mermaid 图表渲染器等大量小文件）
3. 真实构建后端 wheel、创建虚拟环境并安装
4. 真实启动调试服务（`scripts/dev-server.sh start`），确认 `/health`
   健康检查通过，并跑了项目自带的测试数据灌入脚本

这个流程让文件数从 3407 涨到 23703（新增 20296 个文件），构成为：
`frontend-v3/node_modules`（15378）、`backend/.venv`（4090）、
`backend/peekview/static`（397，前端构建产物被复制进了后端*源码包内部*，
不是一个独立的顶层目录）、`backend/peekview/*/__pycache__`（分散在
`api/`、`services/` 等真实源码目录内部，不是集中在一个顶层位置）、
`backend/dist`（构建出的 wheel 文件）。

**实测结果（好消息）**：在这个"构建+调试运行后"的脏状态下直接跑
`repomap_lite`，输出完全干净——2836 个真实源文件被正确识别，
`node_modules`/`.venv`/`static`/`__pycache__`/`dist` 里的全部 20296 个
新增文件零泄漏，因为这些路径全部已经被 peekview 自己的 `.gitignore`
声明覆盖（`__pycache__/`、`backend/peekview/static/`、`backend/dist/`、
`.venv/`），而本工具默认会读取项目自己的 `.gitignore`。

**但深挖为什么"正好"没出问题时，发现了一个真实的正确性 bug**：
`GitignoreMatcher.is_ignored()` 单独调用时，只检查传入路径自身是否匹配
某条规则，**没有检查这个路径的任何一级祖先目录是否已经被规则标记为
"整个目录忽略"**。早期实现的代码注释声称"目录被忽略后，其下所有文件也
一并忽略"这件事已经处理好了，但只是描述了意图，从未真正在代码里实现。
之所以此前的四个验证场景和 Redis 语料复测都没暴露这个 bug，是因为唯一
调用这个函数的地方（`iter_source_files`）用 `os.walk` 的目录剪枝规避了
问题——被忽略的目录从来不会被下钻遍历，其内部文件自然不会被单独拿去
调用 `is_ignored()` 判断。但这只是**调用方恰好用了一种规避了 bug 的
遍历方式**，不代表 `is_ignored()` 本身是对的：直接对文件路径调用
`is_ignored('backend/peekview/static/assets/foo.js', is_dir=False)`
会错误返回 `False`（未被忽略），尽管 `backend/peekview/static/` 整个
目录已经在 `.gitignore` 里被排除。用真实 peekview 数据验证：这个 bug
在没被修复之前，会导致 20296 个新增文件里的 20275 个被 `is_ignored()`
直接判定为"未忽略"（只有已经被 `os.walk` 剪枝挡在外面的极少数路径幸免）。

**修复**：`is_ignored()` 改成先检查 rel_path 的每一级祖先目录是否被判定
为目录级忽略，只要有任意一级祖先被忽略就直接返回 `True`，不再依赖调用方
恰好用对遍历方式来规避这个问题。修复后用相同的 peekview 数据重新验证：
直接调用 `is_ignored()` 对全部 20296 个新增文件都能正确返回 `True`；
同时重新跑了此前全部四个 `.gitignore` 验证场景（含最容易受影响的否定
模式场景）和 Redis 语料的逐文件 diff，确认零回归——真实 CLI 的最终输出
在修复前后完全一致（因为 `iter_source_files` 的目录剪枝本来就规避了这个
bug 对最终结果的影响），修复的价值在于让 `is_ignored()` 这个函数本身
在任何调用方式下都是对的，而不是依赖一种恰好正确的使用方式。

**这条记录的方法论意义**：这是本文件里第N次印证"只用干净的最小复现案例
验证过的功能，不代表在真实项目的脏状态下也没问题"。四个精心设计的独立
验证场景全部通过，掩盖了一个只有在"生成文件的目录结构比想象中更深、
更分散"（构建产物没有整整齐齐待在一个顶层目录里，而是渗透进真实源码
目录内部）时才会暴露的 bug。这也印证了用户建议的验证方法（不要只
clone 仓库直接跑，而是先走一遍真实的构建/调试流程再测）本身就是一种
更贴近真实使用场景、更容易发现这类 bug 的测试策略，值得作为以后验证
新功能的标准做法之一。

## 自动生成文件检测：内容标记，作为适配器的可选能力（而不是全局正则列表）

上面记录的 `.gitignore` 支持解决的是"生成物集中放在一个独立目录"这种
情况，但还有另一种常见模式完全不同：生成的源码文件跟手写代码混在
**同一个目录**里，不靠路径区分身份，靠文件内容自带的"本文件是自动生成的"
标记声明——这在真实项目里非常常见（protobuf/gRPC 生成的桩代码是最典型的
例子），而且**每种语言的标记格式完全不同**，目录名黑名单和 `.gitignore`
这两套基于路径的机制对这种情况完全无能为力。

**架构设计**：第一版实现（已废弃）把全部语言的标记正则写成
`repomap_lite.py` 里的一份全局列表，这违背了整个适配器架构"新增语言
不需要改动核心调度代码"的设计原则——用户明确指出这一点后重新设计：

- `adapter_base.py` 的 `LanguageAdapter` 协议新增一个**可选**方法
  `is_generated(lines) -> bool`，默认不实现（`adapter_says_generated()`
  会安全地处理"适配器没实现这个方法"和"适配器实现了但抛异常"两种情况，
  统一当作"不是生成文件"处理）——这保证了新增这个能力**不需要改动任何
  已有适配器**，只有语言本身有明确的、广泛使用的生成文件标记约定时，
  才值得去对应的适配器里补上这个方法。
- `adapter_utils.py` 新增共享的 `matches_generated_file_markers()` 函数，
  负责"取文件前N行、逐条模式匹配"这个通用扫描机制；具体的标记正则由
  各个适配器自己提供并维护，语言相关的知识留在语言自己的适配器文件里，
  不在核心代码或共享工具函数里出现任何具体语言的标记文案。
- CLI 新增 `--include-generated` 开关，语义上跟 `--include-vendor`/
  `--no-gitignore` 是同一套"默认过滤、显式关闭"的设计一致性。

**已用真实工具输出验证的两个语言**：
- **Go**：`// Code generated ... DO NOT EDIT.`（go.dev 官方规范
  https://go.dev/s/generatedcode，`cmd/go` 工具链自身也依赖这条规则）。
  用真实 `protoc-gen-go` 生成的 `.pb.go` 文件验证：修复前该文件的
  `struct`/方法完整出现在地图里，修复后正确整体跳过。
- **Python**：protobuf 和 gRPC 各自的标记文案（`# Generated by the
  protocol buffer compiler.  DO NOT EDIT!` / `# Generated by the gRPC
  Python protocol compiler plugin. DO NOT EDIT!`）。用真实
  `python -m grpc_tools.protoc` 生成的 `*_pb2.py`/`*_pb2_grpc.py` 验证：
  修复前 gRPC 生成的 `FooStub`/`FooServicer` 桩代码类完整出现，修复后
  正确整体跳过。

**举一反三排查了其他语言，如实记录哪些验证过、哪些没有**：
- **Rust**：构建了真实项目并引入真实依赖（`serde`，会触发 build script
  执行）。确认 Rust 生态没有"生成 .rs 源文件散落在项目源码目录里"这种
  模式——`derive` 宏在编译期展开，不产出独立源文件；真正会写文件的代码
  生成工具（`prost-build`、`bindgen` 等）也是写进 `target/`（已被目录
  黑名单覆盖，用真实 serde 构建产物验证过）。**结论：Rust 不需要
  `is_generated`，现有的目录级排除已经覆盖了实际风险**，这是一个通过
  真实测试得出的负向结论，不是没有测试。
- **Java**：`@Generated`（`javax.annotation.processing.Generated` /
  `jakarta.annotation.Generated`，JSR 269 规范定义）是标准化的注解，
  已经加入 C 系适配器的 Java 方言配置。**如实说明验证程度的局限**：
  这条规则依据的是规范文档和主流注解处理器（Dagger/AutoValue/MapStruct
  等）的公开约定，不是像 Go/Python 那两条一样用真实工具跑出来的输出
  直接验证过的——本次没有网络权限拉取这些工具的 jar 包，Lombok
  虽然装了但它是编译期字节码改写，不产出中间 `.java` 源文件，验证不了
  这条规则。只做了两类间接验证：(1) 对照 JSR 269 文档列出的几种真实
  语法形式（`@Generated("...")`、`@javax.annotation.processing.
  Generated(...)`、带 `value=`/`date=` 参数的完整形式）逐一测试正则
  都能正确匹配；(2) 构造了一个包含"@Generated"字样但只是普通注释、
  不是真实注解的手写文件，确认不会被误判排除。如果这条规则在真实项目上
  出现误判或漏判，优先怀疑是这里，不要默认它跟 Go/Python 那两条同等可靠。
- **C#/C++**：没有添加 `is_generated`。C++ 没有跨编译器/跨工具链统一的
  生成文件标记约定（不同代码生成器各自为政）；C# 有类似 Java 的
  `[GeneratedCode]` 特性但本轮没有时间做同等程度的验证，如实留白，
  不是遗漏，是明确决定不在没有把握的情况下加规则。

**已知局限**：
- 只检查文件开头若干行（Go/Python 5行，Java 因为标记通常在 package
  声明和 import 之后才出现，放宽到50行）——这是为了避免全文扫描增加
  "手写代码某处偶然提到 generated 这个词"的误判风险，代价是如果某个
  工具把标记放在比这更靠后的位置，会漏检
- 不做"文件内容摘要留档"式的语义级生成文件识别（比如通过 diff 历史
  提交判断这个文件是不是每次构建都被覆盖），只做基于当前内容的静态标记
  匹配，跟本工具"零依赖、纯正则/状态机"的整体定位一致

## `.repomapignore` 和 monorepo 子目录扫描（用户提出的产品设计问题引出的两项修复）

用户提出四个产品设计问题："`.gitignore` 之外能不能自定义排除？""排除
规则要不要自动更新？""输出位置/名称能不能自定义、能不能按范围生成多个
地图？""生成的 REPOMAP.md 建不建议提交到版本控制？"。这些问题促成了
一次针对性排查，其中第三个问题在验证"已有能力是否已经支持"的过程中
发现了一个真实的 bug。

### 新增：`.repomapignore`（对应"自定义排除"问题）

`.gitignore` 和 `.repomapignore` 回答的是两个不同的问题——前者是"这个
路径要不要被 git 追踪"，后者是"这个路径要不要出现在地图里"。真实存在
但只有后者场景无法用 `.gitignore` 覆盖的情况：项目里**确实提交到 git**
的第三方代码快照、vendored 依赖、测试 fixture 等——这些内容需要被
版本控制，但对理解"项目实际怎么写的"没有信息量。复用了跟 `.gitignore`
完全相同的解析器和嵌套语义（`GitignoreMatcher` 现在按固定顺序同时加载
`.gitignore` 和 `.repomapignore` 两种文件名，`.repomapignore` 的规则
排在同目录 `.gitignore` 规则之后），不是重新发明一套语法。用真实场景
验证过：git 已经 `add` 追踪的文件，只在 `.repomapignore` 里声明排除，
确认能正确从地图里消失，且 `--no-gitignore` 能同时关闭两者。

**要不要自动维护/更新**：不需要，也不应该。这是跟 `.gitignore` 地位
相同的、项目组主动维护的静态配置。自动化判断"这个路径不值得展示"存在
真实风险——新增的真实代码可能被自动逻辑误判为噪音，从地图里悄悄消失，
且没人会注意到，这比"忘记排除一个生成目录、地图里多了点噪音"严重得多。
这个判断本质上需要人类/项目意图介入，不适合自动化。

### 修复：`--root` 指向子目录时，实际扫描范围没有生效（对应"按范围生成
多个地图"问题）

在验证"能不能按范围生成多个地图"这个问题时，先假设"这应该已经可以用
`--root` + `-o` 组合实现"，实际验证后发现**假设不成立**——`--root`
参数虽然存在，但 `find_repo_root()` 总是从给定路径向上找到 `.git`
所在处，然后把这个结果**同时**当作"实际遍历的起点"和"路径显示基准"，
导致从 monorepo 子包目录下指定 `--root .` 运行时，实际行为退化成
"遍历整个仓库"——用真实的两包 monorepo 复现确认过：从 `packages/pkg-a`
下运行，本以为只会得到该子包自己的符号，实际拿到的是整个仓库的地图，
混入了 `packages/pkg-b` 的内容，`--root` 参数名字暗示的"限定扫描范围"
完全没有生效。

修复：把"扫描范围的起点"（`scan_root`）和"`.gitignore` 规则/输出路径
的基准"（`repo_root`）拆成两个独立概念——`iter_source_files()` 从
`scan_root` 开始遍历，但传给 `GitignoreMatcher.is_ignored()` 判断和
最终输出的路径始终是相对 `repo_root` 的完整仓库相对路径（不是相对子包
自己的路径），这样即使只扫一个子包，输出里的路径依然是
`packages/pkg-a/src/foo.py` 这种一望而知的完整路径，不会让人误以为
这是整个仓库的地图。用真实 monorepo 复现验证：修复后从子包目录指定
`--root .` 只返回该子包自己的符号；额外验证了
`--root <子包> -o <子包>/REPOMAP.md` 的组合能正确支持"每个子包各自
一份地图"的工作流，确认不需要为此单独设计一个"批量生成多地图"的新功能
——这是"先验证已有原语是否已经足够，而不是不假思索地为每个新场景加
新接口"这条原则的一次实践：只有验证后发现原语本身有 bug 时才去修 bug，
而不是绕开 bug、另起炉灶加一个新功能来掩盖它。

### 输出位置/名称本来就可自定义，无需新增功能

`-o`/`--output` 早已支持任意路径和文件名，这条不需要新工作，只是在
`SKILL.md` 里补充说明清楚，跟上面两条一起构成"按范围生成多个地图"这个
完整答案的三个组成部分（自定义位置 + 自定义范围 + 组合调用）。

### 是否建议提交 REPOMAP.md 到版本控制：默认不建议，当作可重新生成的
临时产物，但不做技术性阻拦

这纯粹是一个产品建议问题，没有对应的代码修改，结论和理由记录在
`SKILL.md` 里："过时的地图比没有地图更危险"（本工具生成成本极低，
现场生成的确定性远高于依赖人工记得同步更新并提交的地图）+ 合并冲突
问题（两个分支的地图内容几乎必然冲突，且这个冲突没有实际意义）。同时
如实说明了"团队自己选择提交"也是合理选择的例外情况（人和 agent 都想
零延迟打开、或者生成耗时已经不可忽略的大仓库场景），不做非黑即白的
断言。

## 当前仍然存在的已知局限（未修复，如实列出）

### C++ 的宏与模板元编程（影响面最大的未解决问题）
nlohmann/json 大量使用宏（`JSON_CATCH`、`JSON_HEDLEY_DEPRECATED_FOR` 等）和
模板元编程技巧，真实 tree-sitter 基准因为有完整的 C++ 语法树，能正确跳过宏、
理解嵌套模板；本适配器基于正则+花括号计数，对这类代码的识别率明显更低
（该项目是所有已测项目里表现最弱的一档）。这不是某个具体 bug，而是正则
方案在面对宏展开和复杂模板语法时的系统性局限，没有计划修复（完整支持
需要实现预处理器和模板解析，超出本方案的合理范围）。

### C++ 的 `R"delim(...)delim"` 自定义分隔符原始字符串不处理
分隔符可以是任意字符序列，正则/状态机方式难以在不引入完整解析器的前提下
稳健支持。如果代码大量使用，字符串内容仍可能干扰深度追踪。

### 多行函数签名只显示首行
参数列表跨多行时，输出只保留签名的第一行，不完整展示全部参数。真实基准
会展示函数体的 2-4 行预览，本工具目前完全不做这个（这也是本文件"raw口径"
数字偏低的部分原因——基准展示的预览行在符号级对比里被算作"额外的符号"）。

### 模板/泛型的复杂嵌套可能造成误判
C++ 的 `template<...>` 前缀、Java/C#/Rust 的泛型 `<T>` 只做尽力而为的匹配，
未做完整的尖括号平衡解析，深度嵌套的泛型（尖括号里再套尖括号+逗号）
可能导致方法签名匹配不准确。

### Rust 宏定义不识别
`macro_rules! foo { ... }` 完全不生成符号。`where` 子句的复杂泛型约束
同样只做尽力而为的匹配。

### Shader 适配器不区分入口点约定
不识别 GLSL/HLSL 的 vertex/fragment/compute shader 入口点特殊标注
（如 HLSL 的 `[numthreads]` compute kernel 标注），一律按普通函数处理。

### Vue 单文件组件只解析 `<script>` 块
`<template>` 部分（包括其中的插值表达式、指令、组件引用等）完全不解析，
这是刻意的范围限定——模板不是"定义"。

### 大仓库输出体积（已解决，见下方专门章节；此条保留作为历史记录）
早期版本只有软性的行数警告（超过约1万行在 stderr 提示），不做任何裁剪，
真正大规模仓库（数万文件级）会产出体积很大的地图（真实测过 TypeScript
编译器仓库，13.8MB/44万行），警告只是提醒，不会自动帮用户做决策——
用户直接指出这个场景下"agent 直接读这么大的文件会不会有问题"，促成了
后续的"字节预算自动降级"机制（见"超大仓库：自动降级为索引优先"一节），
现在默认行为已经不再是"警告后放任不管"，而是超过预算自动收起完整细节、
只保留索引，这条限制记录本身已经不再准确描述当前行为，保留是为了
记录问题是怎么被发现和解决的这条完整线索。

### 超大仓库：自动降级为"索引优先"，解决"agent 直接读取巨大 REPOMAP.md
可能失败或耗尽上下文"的问题

用户提出的具体场景："针对大文件仓库，很可能生成一个好几MB甚至几十MB的
repomap，agent一读那不就挂了？"——这是对上一条"大仓库输出体积"限制的
直接追问，从"这是个已知局限"推进到"这个局限该怎么解决"。

**修复的两层机制**（配合前一次会话新增的顶部文件索引一起工作）：
1. 完整展开的逐符号内容超过字节预算（默认2MB）后，后续文件只出现在
   索引里（带真实符号数），不再展开完整 block。
2. 索引本身也有独立的文件数上限（默认500个，按符号数从多到少排序），
   因为验证时发现即使不展开细节，索引本身在文件数极多的仓库下也能长到
   二十多万字符。

两层机制都遵循同一个原则：**可以不展开细节，但不能让文件的存在完全从
产出物里消失、用户/agent 无从得知**——被截断的部分总是有一行聚合计数
说明"还有多少、可以怎么单独获取"，不是静默丢弃。

**开发过程中的一次真实自我纠正**：最初的实现用"符号总数"作为预算单位，
理由是"符号数是已经算好的、更直接反映内容多少的量"。用真实 Redis 语料
验证时发现这个假设站不住脚——测出平均约62字节/符号，但用一个函数签名
风格更冗长的合成测试仓库验证同一个预算数值时，实际输出体积超过3MB，
完全没达到"把体积控制在安全范围"这个机制本该解决的目标，因为核心问题
从一开始就选错了衡量单位：真正决定"agent 读这个文件会不会有问题"的是
字节数本身，不是"符号数"这个因语言/风格而异的间接代理指标。改成直接
以渲染后的 UTF-8 字节数为预算之后重新验证：从5000文件到100000文件的
一系列合成测试仓库，不管符号密度/文件数如何变化，最终输出体积都稳定
收敛在预算值附近（默认预算下约2.1MB），不再随仓库规模线性膨胀。这个
教训值得记录：**选择一个"看起来已经算好、用起来方便"的间接指标去代表
真正关心的目标，本身是需要验证的假设，不能因为这个指标计算起来方便
就默认它和目标是线性对应的关系。**

真实验证过的规模：5000文件（约50000符号，未超预算，完整展开）、10000
文件（约100000符号，超预算，正确降级到2MB+索引）、30000文件和100000
文件的极端合成测试（均正确稳定收敛在预算附近，不随文件数继续膨胀）。
同时确认了 `--force-full-detail`（完全关闭降级）、
`--full-detail-budget-bytes`（自定义预算）、`--index-max-entries`
（自定义索引上限）三个参数都按预期工作，以及 `--update-file` 增量更新
路径不受这个预算影响（增量更新操作的是单个文件，套用全仓库预算语义
上说不通，见 `update_single_file` 的文档字符串）。**增量更新会保留
被截断文件的存在信息**：解析已有地图时同时解析顶部索引段，被截断
（仅索引、无完整 block）的文件会作为 index_only 条目保留并在重建时
合并回索引，不会因为增量更新而从地图里静默消失（早期版本曾因解析只
收集完整 block 而导致这些文件在增量更新后全部丢失，已修复并有
`scripts/tests/test_repomap_lite.py` 里的 pytest 回归测试：增量后的索引
与全新全量生成的索引逐条一致）。

### 索引展示截断 + 增量更新 = 第二处数据丢失（已修复，根因记录）

`--index-max-entries`（默认 500）和 `full_detail_byte_budget`（默认 2MB）
是**两个独立**的截断机制，不能混为一谈：

1. `full_detail_byte_budget` 决定"每个文件是否展开完整逐符号 block"——
   超出预算的文件退化成"仅索引条目"（有路径+符号数，无 block）。
2. `index_max_entries` 决定"顶部索引本身**展示给人看**多少行"——超过
   上限的文件在可见索引里只被压缩成一行聚合计数。

早期版本只实现了机制 1 的索引保留（`parse_existing_map` 只解析可见索引
行），漏掉了机制 2 的情况：当两个机制**同时触发**（数万文件级仓库 + 索引
展示也超 500 行）时，排在索引第 500 名之后、又没有完整 block 的文件，
其路径+符号数**根本没有被写进磁盘**——不是退化成"仅索引条目"，是连索引
条目都没有。用真实的一万文件测试仓库复现过：一次简单的 `--update-file`
就会让数千个文件从地图上彻底消失，且增量更新之前它们只以一行聚合计数的
形式存在，完全无法恢复身份。

修复方式：`render_index` 在展示截断发生时，把"展示之外"的完整
`(path, count)` 列表序列化进一段机器可读存档注释
（`<!-- INDEX-ARCHIVE-BEGIN ... INDEX-ARCHIVE-END -->`，每行
`count\tpath`，用 tab 分隔因为路径可能含空格）。人类阅读 REPOMAP.md 时
自然跳过这段注释，但 `parse_existing_map` 能精确解析回完整列表——
可见索引行和存档段两处来源分别解析、合并、防御性去重（保留第一次出现的
计数），再排除掉已有完整 block 的文件。这样"只要文件曾经出现过（可见
索引里或存档段里），它的路径+符号数就不会在增量更新中丢失"。

回归测试见 `scripts/tests/test_repomap_lite.py` 的
`test_incremental_update_beyond_index_display_cap_does_not_lose_files`
（600 文件 + 小字节预算，同时触发两层截断，断言增量前后
`blocks + index_only` 总数恒等于真实文件数）。

这个 bug 的隐蔽性在于它需要**两个独立机制同时触发**才暴露——单独测
"预算降级"或单独测"索引展示截断"都测不出来。教训：**多个降级/截断机制
叠加时，必须验证叠加场景，不能只各自单独验证**。

### 诊断/对比脚本本身的已知噪音（不是产品缺陷，但会让数字看起来更差）
用于生成上述基准数据的对比脚本用简化正则从渲染后的文本行里再抠一次符号名，
存在两类已确认的噪音来源：
- 真实基准展示的"函数体预览行"（跟在定义行后面的局部变量、嵌套闭包等）
  会被误当作独立符号统计，拉低 raw 口径的 precision/recall（这也是本文件
  统一给出 raw 和 flat-only 两种口径的原因）。
- 对比脚本自身的关键字识别覆盖不全（比如早期不认识 C 语言无关键字的
  `[修饰符]* 类型 函数名(...)` 风格、C# 逐字字符串、Rust 的 `pub`/`mod`/
  `impl...for`语法、宏前缀函数），本轮会话过程中已经针对性修补过多次，
  每次都对最终数字有明显影响（例如 C 语言支持从"看起来 20% 精度"修正到
  "确认 96%+ 精度"，全部差距来自对比脚本本身，不是 `repomap_lite` 的
  真实缺陷）。这个教训本身值得记录：**任何用于验证的工具都可能有自己的
  bug，数字反常时先怀疑测量方法，再怀疑被测系统**。

## 完全不支持的技术栈

以下不在当前 12 个适配器的覆盖范围内，遇到这些文件会被直接判定为
`unsupported` 跳过，不会出现在 REPOMAP.md 里：

- Kotlin、Swift、PHP、Scala、Dart 等其他语言
- SQL、HCL/Terraform 等其他配置/构建类文件
- Svelte、Astro 等 Vue 之外的其他单文件组件格式

新增这些语言的支持路径见 `references/adapter_guide.md`，架构上是可扩展的，
只是尚未有对应的适配器实现。Rust 和 Ruby 已经在本轮会话中从"不支持"变为
"支持且实测有意义"（Ruby 的数字需要按上文"参考基准本身存在方法提取缺口"
那一节的说明来解读，不能直接看 precision 数字），Makefile/Dockerfile
也从"不支持"变为"支持，但没有参考基准可比较，按适配器文档字符串里的
说明理解覆盖范围即可"。这些都是同一个可扩展架构反复验证成功的例子；
如果继续扩展，参照 `adapter_guide.md` 里记录的经验（尤其是"注释与字符串
边界必须统一在一次扫描里处理，不能拆成独立阶段"这一条，以及"修复一个
误报前先构造一个会被新逻辑误伤的合法场景去验证"这一条），预计能避免
重新踩这几轮踩过的坑。
